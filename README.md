# telegram-grok-wake

Продолжить общение с Grok Bot можно и в Telegram.

Связка **Telegram → Telegram Serverless → рутина Grok Bot**: бот в Telegram доставляет сообщения в Grok Bot, а компьютер бота не нужно держать включённым ради опроса `getUpdates`.

Основной (и единственный в этом пакете) путь — папка `serverless/`: код выполняется на инфраструктуре Telegram, webhook ставит сама платформа.

---

## Зачем это

Сообщения из Telegram нужно как-то доставить до Grok Bot. Есть два пути:

1. **Опрос (polling)** — скрипт на компьютере Grok Bot постоянно спрашивает Telegram: «есть новое?» Минус: скрипт должен крутиться без остановки. Ушёл компьютер в спячку или перезапустился — связь оборвалась.
2. **Webhook + serverless** — Telegram сам присылает сообщение маленькому помощнику, помощник будит Grok Bot. Этот пакет — второй путь.

## В чём загвоздка

Telegram умеет прикладывать к webhook только свой секрет в заголовке `X-Telegram-Bot-Api-Secret-Token`. Grok Bot, **по документации** рутин, ждёт заголовок `Authorization: Bearer <ключ>`. Поэтому нужен посредник: принять обновление от Telegram, проверить, что писать боту можно, и разбудить рутину уже с правильным заголовком.

## Схема

```
Telegram
   │  обновление (webhook ставит сама платформа Serverless)
   ▼
Telegram Serverless  (папка serverless/)
   │  1. только личка и id из списка (owner_id + allowed_ids)
   │  2. повтор того же update_id отбрасывается, лимиты пробуждений
   │  3. в чате «думаю…» и статус «печатает…»
   │  4. POST события на webhook рутины
   │     Authorization: Bearer <ключ>
   │     до 4 попыток; не вышло — сообщение уходит в dead letters,
   │     отправитель получает уведомление с просьбой повторить
   ▼
Рутина Grok Bot  →  думает  →  npx tgcloud run endpoints/box (op: send, token = reply.token)
   ▼
Тот же чат Telegram (первый send правит «думаю…»)
```

Мост **ждёт** ответа webhook рутины в том же запуске обработчика (отдельного `waitUntil`, как у Cloudflare Workers, в документации Telegram Serverless нет), поэтому повторы короткие: суммарно около 10 секунд ожидания.

## Что приходит в рутину

JSON с `type: "telegram_message"`:

- `message` — текст, тема, пересланное/цитата (помечены как чужие данные), вложения **только как метаданные** (скачивать их в этом пакете нечем);
- `sender_role` / `sender_is_owner` — владелец или гость;
- `history` — предыдущие сообщения этого чата и темы;
- `reply` — `token` (~30 минут, привязан к чату и теме), `expires_at`, `op: "send"`, `placeholder_message_id`.

Токена Telegram-бота в событии нет. Поле `reply` и операция `send` — **наша схема**, не официальный API Grok Bot; из документации Grok Bot нужен только заголовок `Authorization: Bearer`.

## Ответ в Telegram

`npx tgcloud run endpoints/box '{"op":"send","token":"<reply.token>","text":"…","final":true}'`

- Пока не указано `final: true`, одним токеном можно отправить несколько частей. После успешного `final: true` токен больше не принимается.
- Если отправка не удалась (ошибка Telegram), `final`-токен возвращается, и ту же команду можно повторить. Если часть сообщений уже ушла, при повторе она может продублироваться.
- Текст длиннее 4096 символов режется на части: первая правит «думаю…», остальные уходят новыми сообщениями.

## Настройка

Кратко (полный пошаговый гайд — в [SKILL.md](SKILL.md)):

1. Создай **нового, отдельного** бота у [@BotFather](https://t.me/BotFather) и включи у него Serverless.
2. В папке `serverless/`: `npm ci`, `npx tgcloud login` (нужен CLI access token из @BotFather → бот → Serverless → CLI Access, это не токен бота), `npx tgcloud push`.
3. В Grok Bot создай рутину с webhook-триггером, скопируй **POST to** и **key**.
4. Запиши настройки:

```
npx tgcloud run endpoints/box '{"op":"config_set","values":{"owner_id":"YOUR_TELEGRAM_USER_ID","allowed_ids":"","routine_url":"YOUR_GROK_WEBHOOK_URL","routine_key":"YOUR_GROK_BEARER_KEY"}}'
```

5. Проверь: `npx tgcloud run endpoints/box '{"op":"config_status"}'` → `"ready": true`.
6. Инструкцию рутины возьми из [ROUTINE_PROMPT.md](ROUTINE_PROMPT.md).

Секреты в файлы пакета не вписывай.

Можно поднять такого помощника и на своём сервере, но этот пакет его не включает.

### Параметры `config_set`

| Ключ | Значение |
|---|---|
| `owner_id` | Твой числовой Telegram id. Без него не проходит никто. |
| `allowed_ids` | Необязательно: id гостей через запятую. Лучше не использовать (см. «Безопасность»). |
| `routine_url` | Адрес рутины, только `https://`. Пустое значение очищает параметр (мост перестанет принимать сообщения). |
| `routine_key` | Ключ рутины. В ответах команд целиком не показывается. |
| `max_wakes_per_min` | Пробуждений в минуту на один чат (по умолчанию 12). |
| `max_wakes_per_hour` | Пробуждений в час на весь мост (по умолчанию 60; у самой рутины потолок 200 запусков в час). |
| `history_messages` / `history_max_chars` / `history_days` | Сколько истории класть в событие и как долго хранить (20 / 8000 / 30 дней). |
| `reaction` | Эмодзи-реакция на принятое сообщение (по умолчанию 👀). |

Служебные команды в чате с ботом: `/start`, `/ping`, `/status`, `/reset` (`/new`).

## Безопасность

- Проходят только личные чаты, где `chat.id == from.id`, и id из списка. Пустой список — никто. Всё остальное игнорируется до записи в базу.
- Текст из Telegram — недоверенный ввод, а у рутины есть терминал. Гостей отличает от владельца только инструкция в `ROUTINE_PROMPT.md` (защита промптом, не кодом), поэтому надёжнее гостей не добавлять.
- На компьютере рутины лежит CLI-токен Serverless: с ним можно менять код и базу бота. Поэтому для моста заводи отдельного бота.
- Токен ответа — подпись HMAC на ~30 минут, привязана к чату и теме; сам по себе он не работает: `send` вызывается только через `npx tgcloud run`.
- `routine_url` принимается только по `https`, чтобы ключ не ушёл открытым текстом.
- Переписка и события хранятся в базе бота (по умолчанию 30 дней). `routine_key` и ключ подписи лежат в таблице `kv` открытым текстом, снаружи она недоступна: Mini App у бота нет, а единственный endpoint отвергает любые вызовы с init data.

## Ограничения

Набросок, не готовый продукт.

- Вложения не скачиваются: в событие попадают только метаданные.
- Повторной отправки недоставленных сообщений нет: `op: deadletters` показывает их, `op: mark` помечает вручную, отправитель получает просьбу написать ещё раз.
- Обработчик «Стоп» (`stopped_message_generation`) только записывает факт нажатия; потокового ответа в этом пакете нет.
- Формат события — договорённость моста, точный вид задаёт инструкция рутины в приложении Grok Bot.
- Реальные токены и ключи не коммить.
